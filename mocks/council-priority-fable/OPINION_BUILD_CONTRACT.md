# OPINION — one-shot buildout plans, then argue, then forge one bible

**Seat:** FABLE · **Asked by:** Bailey via Blaze · **Scope:** opinion only. No plan, no Land, no questions.

## 1. Is this the right next Council move?

**Yes, with one condition: it runs after the nav pick and does not touch rows 1–6.**

Why yes. The last two days showed the failure the proposal is aimed at: three seats each read the repo, the open PRs and the brief separately, then converged only through rebuttal rounds. That convergence produced good rulings (PR #36 only, share modes as a port, CCO money authority, no crew product) but it happened *after* Lands were already open. A decided bible before the next-cycle Lands (client door, one-tenant status pilot, master "waiting on whom" home, close-out) is exactly the missing artifact: it lets Grok cut instead of choosing, and it lets Latch prove against something written down instead of against a seat's memory.

Why the condition. Rows 1–6 are already locked and mostly in flight or proof-only. A buildout plan that reopens them is a re-litigation, not a bible. The plans should start where the lock ends: the picked nav master plus the CVP product locks, and describe rows 7–14 end to end.

One more reason to do it: the nav mocks proved that three parallel one-shots plus one pick is a process Bailey can read and decide on from a phone. The same shape for the build contract is a known-good loop, not an experiment.

## 2. What each one-shot plan must contain to be useful

Short, structured, checkable. Every section is a table or a list, not prose. If it can't be checked against a live surface or the repo, it doesn't belong.

1. **Record contract.** The objects and states the whole product hangs on: tenant → project → deliverable → version → review outcome → delivered. Which table or route each lives in today (`co_production.deliverables`, share intent, approval rounds), which is new, which is derived. No status may be typed by hand.
2. **Two-side surface map.** For each screen on the picked nav: side (client door / Content Co-op master), scope (one tenant / all tenants), the record it reads, the write it makes, the phone and desktop version. One row per screen. If a screen makes no write and reads no record, it is cut.
3. **Tenant + door model.** How `{client}.co-videopro.com` resolves a tenant, what a tenant can never see, how the generic door coexists until per-client doors Land, and what is *not* changed (DNS is a Bailey gate; guest links keep working).
4. **The rituals, as sequences.** Review round (guest taps, finishes, outcome lands), status read (master "waiting on whom"), close-out for ACS. Each as an ordered list of taps with the write at each step. Delivery described as a *fixed record + swappable stage*, never as a step list.
5. **Land order with proof text.** Rows in dependency order, each with: files touched, done-when on the live surface, the negative Latch proves, the ledger row it closes, and which live tip it preflights against. Reuse the existing spine numbering so the three plans are comparable row for row.
6. **Named drops.** What the plan deliberately does not build, in one list. A dropped thing that is named is a decision; one that is forgotten is a hole.
7. **Inputs from outside the repo.** Only what Blaze already has or has said he'll supply (tenant list, marks, Madeline's sheet). No new Bailey questions.

Target length: a plan Blaze can read on a phone in ten minutes. Anything longer is a novel and will not be argued, only skimmed.

## 3. The failure mode that wastes Cursor credits

**Three plans that describe the same product in three vocabularies, so the argue-round is spent reconciling words instead of decisions.**

That is what happened in the first debate round: "Caio loop" vs "Caio chip" vs "human rail," "Projects home" vs "waiting on whom," "share modes" vs "share posture." Each rebuttal burned a round translating before it could rule. If the three plans are free-form, Blaze's forge becomes a merge of documents rather than a pick of decisions, and the Kimi bucket goes to rewriting.

Two smaller versions of the same waste:

- **Plans that re-argue rows 1–6 or the product locks.** Any paragraph on whether there should be a crew side, whether share modes wait on the pick, or whether Wistia stays is dead spend.
- **Plans written from the July repo docs instead of the September live trains.** A plan that plans against `STATUS.md` from 2026-07-26 will propose Lands that already exist.

## 4. Changes I'd make before we run it

1. **Issue a fixed template first** (the seven sections above, with row numbers matching the spine). Plans fill the template; they do not invent structure. This alone removes most of the reconciliation cost.
2. **Fix the inputs before the plans start.** Every seat plans from the same four things: the picked nav images, the CVP lock text, the current spine rev 4 rows 7–14, and a one-page list of what is live on `46a256f2` and `c58816e4`. No seat does its own reality tour.
3. **Cap and gate the argue-round.** One rebuttal each, adopt-before-contest, operating reasons only, ending in a per-row table: agree / disagree / evidence. Blaze forges from the tables, not from the prose.
4. **Forge output is the spine plus a bible, not a third document type.** The master lands as a revised `MASTER_SPINE` (rows 7–14 filled to the template's detail) so Grok's pack for each Land is a copy of the row, not a reinterpretation.
5. **Two seats, not three, if credits are tight.** Bailey has already said this pass is Fable + Grok. Two plans argued well beat three plans skimmed. Opus can rejoin at the forge as a reader if Bailey wants a third eye on the bible.
6. **Rows 1–6 keep moving while the plans are written.** Proof on #1 and #2, the pick on #3, Kimi on #5 do not pause for this. The bible governs the *next* cycle's Lands.
